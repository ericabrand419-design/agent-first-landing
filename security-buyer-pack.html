Security / data / governance

Security Buyer Readiness Pack

The buyer-facing explanation of what Agent First stores, how access and client separation work, how rules and AI are governed, and what remains subject to independent technical review.

Current posture: early-stage controls and documented governance. Agent First does not claim SOC 2, HIPAA, PCI, or other certification/compliance status that has not actually been established.

Data flow

1. Approved sources

Customer policies, procedures, approved wording, routing/escalation rules, service eligibility, contacts, hours, and other operational sources.

2. Client Profile / rule layer

Agent First structures the approved material into client-specific configuration and operational guidance.

3. Agent workspace

The active client + current request determine what rule, wording, escalation, documentation, and next action are surfaced.

What Agent First needs—and what it should avoid

Typical operational data

  • Client/account/location configuration
  • Approved rules and scripts
  • User roles
  • Pilot/test measurements
  • Rule/version/audit metadata

Not required by default

  • Full call recordings
  • Payment-card data
  • SSNs
  • Unnecessary end-customer PII
  • Regulated data unrelated to the bounded workflow

Data-minimization rule

Use only the minimum information required for the decision-support workflow. Workflow observation does not automatically authorize screen recording or third-party capture. Any capture service requires explicit customer approval, a defined application/user scope, vendor/data-flow review, and deletion/retention terms. Regulated or highly sensitive data requires explicit scope, contract, architecture, and security review before production use.

Rule and AI governance

Rule ownership

The customer supplies or approves source policy. Each material rule should have a source, owner, version/effective date, and approval state.

Change control

Proposed → reviewed → approved → published → superseded/rolled back. No silent policy change because a model inferred something.

AI / LLM use

Use approved providers, minimize confidential content, review provider data-use terms, and do not treat generative output as the authoritative rule source where deterministic policy can govern.

Operational controls

Logging / audit

Record material admin changes, rule versions, security/access events, and significant automated actions.

Backup / versioning

Maintain recoverable configuration/business records and test export/restore/rollback before relying on them operationally.

Incident response

Named owner → contain → preserve evidence → assess vendor/customer/legal obligations → communicate → review/remediate.

Security questionnaire response library

Buyer questionCurrent answer
Are you SOC 2 certified?No. Agent First is early stage and does not claim certification it has not earned. The company maintains documented security/data controls and is preparing for an independent application/security review.
How is customer data separated?Customer/account access is intended to be logically isolated by authorization and scoped data access. Tenant-boundary testing is required before customer production reliance.
Do you train models on customer data?Agent First’s product policy is to minimize content sent to model providers and review provider data-use terms. Exact provider behavior must be stated from the current vendor contract/configuration rather than assumed.
Who owns customer rules?The customer owns its policies/source material. Agent First owns its software, generic schemas/workflows, and platform configuration methods.
How do you manage rule changes?Through explicit source/version/owner/approval governance; changes are not published solely from AI inference.
What regulated data do you support?Regulated/highly sensitive production data is gated pending use-case-specific legal/security review and appropriate contractual/technical controls.

Independent engineer review gate

Before a paid customer relies on Agent First with real client data, an experienced application/security engineer should review authentication/session handling, tenant isolation, secrets, database access, logs, backup/restore, deployment configuration, dependency risk, API/model-provider exposure, and basic vulnerability testing. High-risk findings must be resolved before expansion.
